## 숫자 야구 · 판정 외의 동작도 테스트하기

**리뷰에서 중점적으로 본 부분.** 과제에서는 잘못된 입력을 처리하고, 콘솔 입출력과 게임 규칙을 분리하는 점이 중요했습니다. 두 번째 작업에 받은 PR 코멘트를 읽고 다음 리팩토링에 반영했습니다.

**당시 내 생각.** 알고리즘 문제를 풀듯 `main()`부터 작성하고, 정답일 때의 출력에 집중했습니다. 그런데 문자가 들어오거나 숫자가 중복됐을 때 프로그램이 어떻게 행동해야 하는지도 먼저 정의해야 했습니다. PR을 주고받으면서 동료가 한 번에 검토할 수 있는 커밋의 크기도 고민하게 됐습니다.

**코드에 반영한 내용.** `ConsoleIO`에서 입력 검증을 `InputValidator`로 분리했습니다. 정수가 아닌 입력, 길이·범위 오류, 중복 숫자, 판정 및 일곱 번의 기회를 모두 사용한 경우를 테스트했습니다. [입력 검증 분리 커밋](https://github.com/jisung1017/internship/commit/e3a17a2) · [숫자 야구 테스트](../assignments_1/test_baseball.py)

**다음에 실천할 일.** 동작 하나를 실패하는 테스트로 먼저 정의합니다. 변경이 제대로 동작하는지 확인한 뒤, 의도를 읽을 수 있는 작은 커밋을 남깁니다.

## 키오스크 · 주문의 전체 흐름 먼저 보기

**받은 피드백.** 첫 키오스크 리뷰에서는 값이 대입됐는지 확인하는 테스트보다 경계값과 결제·재고 차감 같은 핵심 흐름에 집중하라는 피드백을 받았습니다.

**당시 내 생각.** 주문 전체를 따라가기 전에 작은 객체부터 설계하고 테스트했습니다. CLI를 만든 뒤에야 샷을 추가하면 원두도 더 필요하다는 요구를 놓쳤다는 걸 알아차렸습니다. 이 규칙을 나중에 넣으려니 모델도 테스트도 함께 바꿔야 했습니다. 다음에는 인수 시나리오에서 시작하자고 회고에 적었습니다.

**코드에 반영한 내용.** 장바구니 항목의 재료 요구량에 기본 음료와 선택한 옵션의 레시피를 합쳤습니다. CLI 인수 테스트에서 기본 음료는 원두 18단위, 샷 두 개를 추가한 음료는 38단위를 소비합니다. 재고가 부족할 때 수량이 그대로인지 별도로 확인합니다. [장바구니 항목의 레시피 계산](../assignments_2/src/domain/cart_item.py) · [주문 인수 테스트](../assignments_2/tests/test_acceptance.py)

**다음에 실천할 일.** 주문 시나리오를 먼저 작성하고 정상 범위의 최소·최대, 그 바로 바깥의 값, 0이나 빈 선택처럼 의미 있는 예외를 정리합니다.

## 키오스크 · 주문 흐름에 맞게 API 설계하기

**받은 피드백.** 8월 4일 리뷰에서는 요청 사이에 누가 장바구니를 관리해야 할지 짚었습니다. 8월 6일에는 ORM을 거치는 흐름과 Swagger에서 어떤 요청을 보내야 하는지 설명이 부족하다는 점이 드러났습니다. 8월 10일에는 사용자 흐름을 다시 살피며 옵션 ID와 메뉴 필터가 논의됐습니다.

**당시 내 생각.** 처음에는 CLI 흐름을 거의 그대로 HTTP에 옮겼습니다. Swagger에서 응답이 오는 건 확인했지만, 값이 어디서 왔고 처음 보는 사람이 어떤 요청을 보내면 되는지 설명하기 어려웠습니다. 고객이 메뉴를 고르고 주문을 확정하는 흐름을 따라가면서 결제 단계에서 서버에 필요한 정보를 다시 생각했습니다.

**코드에 반영한 내용.** 주문 서비스가 요청에 담긴 항목으로 매번 장바구니를 구성합니다. 클라이언트는 숫자 옵션 ID를 보낼 수 있고, 메뉴 API는 카테고리·태그 필터와 주문 가능 여부를 제공합니다. 요청 스키마에 주문 예시를 담았고, API 테스트에서 주문 UUID와 `Location` 헤더를 확인합니다. [주문 서비스](../assignments_2/src/application/order_application_service.py) · [키오스크 라우트](../assignments_2/src/interface/api/routers/kiosk.py) · [API 스키마](../assignments_2/src/interface/api/schemas.py) · [주문 API 테스트](../assignments_2/tests/test_kiosk_order_api.py)

**다음에 실천할 일.** 요청 본문부터 서비스와 ORM을 거쳐 응답이 나오기까지 한 번의 주문을 리뷰어에게 설명할 수 있게 정리합니다. 현재 API 테스트는 테스트 대역을 사용합니다. PostgreSQL까지 연결한 흐름은 별도로 검증해야 합니다.

## 키오스크 · 잠금이 보호하는 범위 이해하기

**받은 피드백.** 8월 10일 리뷰 당시 동시 주문을 처리하려고 `with_for_update()`를 사용했습니다. 그 잠금이 무엇을 보호하고 주문에 왜 필요한지 이해하고 사용하라는 피드백을 받았습니다.

**당시 내 생각.** 주문을 하나씩 처리할 수는 있었지만, 주문·입고·취소가 같은 재료의 수량을 동시에 바꾸면 어떤 일이 생길지 이해해야 했습니다.

**코드에 반영한 내용.** 기준 버전은 재고를 읽기 전에 재료 ID 오름차순으로 PostgreSQL의 트랜잭션 수준 advisory lock을 획득합니다. 저장할 때도 잠근 범위를 따릅니다. 주문 상태를 변경하는 경로에는 주문 행 잠금도 적용됐습니다. 테스트에는 주문·입고·취소 요청이 경합하는 시나리오가 있습니다. [재고 잠금 구현](../assignments_2/src/infrastructure/repositories/orm_inventory_repository.py) · [주문 Repository](../assignments_2/src/infrastructure/repositories/orm_order_repository.py) · [동시성 테스트](../assignments_2/tests/test_concurrency.py)

**남은 검증.** 재고를 변경하는 모든 경로가 같은 잠금 규칙을 따르는 범위에서 동작합니다. 포트폴리오 정리 단계에서는 PostgreSQL 동시성 검증을 미뤘으므로 일회용 DB를 사용한 검증이 남아 있습니다.

## 마이그레이션 · 업그레이드 경로 보존하기

**내가 기록한 문제.** 로컬에서 이전 Alembic 리비전 때문에 문제가 생기자 리비전을 교체한 뒤 내 DB에 `stamp`를 적용했습니다. 내 환경에서는 진행할 수 있었지만, 이전 리비전을 참조하는 DB는 업그레이드 경로를 따라갈 수 없었습니다.

**기준 버전에서 확인한 내용.** 저장소에 들어 있는 Alembic 리비전들은 `down_revision`으로 이어져 있습니다. 교체된 예전 리비전을 사용하는 DB가 현재 스키마로 업그레이드되는지는 포트폴리오 정리 단계에서 검증하지 않았습니다. [Alembic 리비전](../assignments_2/migrations/versions/) · [마이그레이션 제약 (영문)](../assignments_2/README.md#getting-started)

**다음에 실천할 일.** 다른 개발자가 이미 적용했을 리비전을 보존합니다. 빈 DB에 처음 설치하는 경우와 기존 데이터가 있는 스키마를 업그레이드하는 경우를 모두 검증합니다.
