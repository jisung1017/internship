# 객체지향 설계 피드백

## 평가 기준

README의 핵심 목표는 TDD 기반 객체지향 설계, 도메인 모델링, UI와 비즈니스 로직의 분리이다. 특히 원시값 포장, 작은 메서드, 테스트 가능한 핵심 로직, 메모리 저장소 사용, 주문/옵션/재고/결제의 책임 분리가 중요한 기준이다.

이 기준에서 보면 현재 코드는 과제 요구사항을 충족하기 위해 필요한 객체들을 잘 분리하려고 시도했다. `Money`, `Quantity`, `Menu`, `Recipe`, `OptionGroup`, `Cart`, `Order`, `Inventory`, `Payment`처럼 도메인 개념을 클래스로 표현했고, CLI와 애플리케이션 서비스도 별도 계층으로 나누었다.

다만 다음 단계의 리팩터링에서는 "클래스를 충분히 만들었는가"보다 "각 객체가 자기 책임을 충분히 갖고 있는가"에 더 집중하면 좋다. 현재 구조는 동작은 잘 분리되어 있지만, 일부 계산과 검증이 `OrderService`, `Menu`, CLI 쪽에 조금 몰려 있다.

## 잘한 점

### 1. 계층 분리 방향이 좋다

`src/domain`, `src/application`, `src/environment`, `src/interface`로 나눈 구조는 과제 요구사항에 잘 맞는다. 콘솔 입출력은 CLI가 담당하고, 주문 흐름은 `OrderService`가 조율하며, 금액/수량/메뉴/옵션/재고 같은 핵심 개념은 domain 객체로 표현했다.

특히 `parse_menu_choice`, `parse_group_selection`, `parse_quantity`처럼 입력 파싱을 함수로 분리한 점은 좋다. 콘솔 입력 없이도 테스트할 수 있고, UI와 도메인 로직을 분리하려는 의도가 보인다.

### 2. 원시값 포장을 적용했다

`Money`, `Quantity`를 별도 객체로 만든 점은 좋은 선택이다. 음수 방지, 타입 검증, 더하기/빼기/곱하기 같은 연산을 값 객체 내부로 넣었기 때문에 단순 `int`를 직접 다루는 코드보다 안정적이다.

`Ingredient`, `Recipe`, `RecipeItem`, `InventoryItem`처럼 도메인에서 의미 있는 이름을 가진 객체를 만든 것도 긍정적이다. 이 객체들은 이후 리팩터링에서 더 많은 행위를 가져갈 수 있는 기반이 된다.

### 3. 결제와 재고 차감 순서를 잘 고려했다

`OrderService.checkout`에서 먼저 재고 가능 여부를 확인하고, 결제에 성공한 뒤 실제 재고를 차감한다. 재고 부족 시 잔액이 차감되지 않도록 한 점은 요구사항을 잘 이해한 부분이다.

`Inventory.can_consume_all`이 복사본으로 시뮬레이션한 뒤 가능 여부를 판단하는 것도 좋다. 여러 메뉴가 같은 재료를 공유할 때, 메뉴별로 따로 검사하지 않고 전체 주문 기준으로 재고 부족 여부를 판단할 수 있다.

### 4. 테스트 범위가 넓다

도메인 객체 단위 테스트, 애플리케이션 서비스 테스트, CLI를 포함한 인수 테스트가 있다. 특히 옵션 선택이 재고 차감에 반영되는지, 재고 부족/잔액 부족 시 장바구니와 잔액이 어떻게 되는지 검증하는 테스트는 과제의 핵심 흐름을 잘 잡고 있다.

## 리팩터링 피드백

### 1. 객체의 책임을 조금 더 객체 내부로 옮기면 좋다

현재 코드는 여러 객체로 잘 나뉘어 있지만, 일부 객체는 아직 데이터를 보관하는 역할이 더 크고 실제 판단은 외부에서 수행한다. 객체지향적으로 더 자연스러운 구조를 만들려면 각 객체가 자신의 상태와 관련된 판단을 직접 하도록 조금씩 옮기면 좋다.

예를 들어 `OrderService.add_to_cart`는 메뉴 옵션을 검증한 뒤 `CartItem`을 만들고 `Cart`에 넣는다. 이 흐름은 "장바구니에 상품을 담는다"라는 장바구니의 핵심 행위에 가깝다. 따라서 다음 단계에서는 `Cart.add_menu(menu, quantity, selected_options)`처럼 `Cart`가 `CartItem` 생성을 포함해 책임지는 방향을 고려할 수 있다.

`checkout`도 마찬가지다. `OrderService`가 주문 생성, 필요 재료 계산, 재고 확인, 결제, 재고 차감, 장바구니 초기화까지 모두 조율하고 있다. 유스케이스 흐름을 담당하는 application service가 필요한 것은 맞지만, 계산 책임까지 너무 많이 갖게 되면 도메인 객체의 역할이 약해진다.

리팩터링 방향은 다음처럼 잡을 수 있다.

- `Cart`: 메뉴와 수량, 선택 옵션을 받아 장바구니 항목을 생성하고 보관한다.
- `CartItem`: 메뉴, 옵션, 수량 기준 총 가격과 필요 재료를 계산한다.
- `Order`: 확정된 주문의 총액과 전체 필요 재료를 계산한다.
- `Inventory`: 주문이 요구하는 재료를 소비할 수 있는지 판단하고 차감한다.
- `Payment`: 주문 금액 결제를 담당한다.
- `OrderService`: 위 객체들을 순서대로 협력시키는 얇은 조율자 역할을 한다.

핵심은 `OrderService`를 없애는 것이 아니라, 서비스가 도메인 계산을 직접 많이 알지 않도록 줄이는 것이다.

### 2. `create_menu`는 문제라기보다 다음 리팩터링 후보에 가깝다

`src/environment/menus.py`의 `create_menu`는 메뉴, 옵션, 재료, 레시피를 한 번에 조립한다. 이 부분은 하드코딩이 많아 보일 수 있지만, 현재 과제처럼 데이터베이스나 외부 설정 파일을 사용하지 않는 환경에서는 어느 정도 자연스러운 선택이다. 애플리케이션이 시작될 때 사용할 기본 메뉴 데이터를 메모리에 구성해야 하기 때문이다.

따라서 이 부분을 단순히 "하드코딩이라 나쁘다"고 보기보다는, 현재는 DB가 없는 환경에서 필요한 composition root 역할을 하고 있다고 보는 편이 맞다. 객체를 직접 생성하는 것 자체가 문제는 아니다.

다만 메뉴가 늘어나거나 옵션 정책이 복잡해질 경우, `create_menu`가 계속 길어질 가능성은 있다. 그래서 다음 단계에서는 "하드코딩 제거"가 아니라 "데이터 정의와 객체 생성 로직 분리"를 목표로 리팩터링하면 좋다.

예를 들어 지금은 한 함수 안에 다음 내용이 함께 있다.

- 재료 이름 정의
- 옵션 그룹 정의
- 옵션별 가격과 레시피 정의
- 메뉴별 가격과 레시피 정의
- 메뉴와 옵션 그룹 연결
- 전체 메뉴 목록 반환

이 구조는 작은 과제에서는 충분히 동작하지만, 메뉴를 추가하거나 옵션을 변경할 때 함수 내부 코드 전체를 읽어야 한다. 리팩터링한다면 먼저 메뉴 정의 데이터를 상수로 분리하고, 작은 팩토리 함수가 그 데이터를 객체로 변환하도록 만들 수 있다.

예시는 다음과 같다.

```python
MENU_DEFINITIONS = [
    {
        "name": "아메리카노",
        "price": 3000,
        "recipe": {"원두": 18, "물": 250, "컵": 1},
        "option_groups": ["temperature", "shot", "syrup"],
    },
]
```

이렇게 바꾸면 여전히 DB 없이 메모리 데이터를 사용하지만, 메뉴 추가는 객체 생성 코드 수정이 아니라 데이터 추가에 가까워진다. 과제 규모에서는 JSON/YAML 파일까지 분리하지 않아도 되고, Python dict나 dataclass 기반 정의만으로도 충분하다.

추천하는 단계는 다음 순서다.

1. 현재 `create_menu` 동작은 유지한다.
2. 재료, 옵션 그룹, 메뉴 정의를 작은 상수나 헬퍼 함수로 나눈다.
3. `create_recipe`, `create_option_group`, `create_menu_item` 같은 변환 함수를 둔다.
4. 테스트는 기존 메뉴 이름, 가격, 레시피, 옵션 구성이 그대로 유지되는지 확인한다.

이렇게 하면 현재 구현의 장점을 유지하면서도 변경하기 쉬운 구조로 갈 수 있다.

### 3. `Recipe`가 계산 책임을 더 가지면 존재 이유가 선명해진다

`Recipe`는 `RecipeItem` 목록을 감싸고 중복 재료를 막는 역할을 한다. 레시피가 "여러 재료와 수량의 묶음"이라는 도메인 개념이라면 별도 객체로 두는 것은 좋은 방향이다.

다만 현재 구현에서는 `Recipe`가 주로 검증된 리스트 역할에 머물러 있다. 레시피끼리 합치기, 메뉴 수량만큼 필요 재료 계산하기, 옵션 레시피와 메뉴 레시피를 합산하기 같은 행위는 `OrderService`, `Inventory`, 반복문 쪽으로 흩어져 있다.

`Recipe`를 더 의미 있는 객체로 만들려면 다음 메서드를 고려할 수 있다.

- `multiply(quantity)`: 레시피를 주문 수량만큼 확장한다.
- `merge(other)`: 다른 레시피와 합치면서 같은 재료 수량을 합산한다.
- `required_items()`: 외부에서 안전하게 사용할 수 있는 필요 재료 목록을 반환한다.

이렇게 하면 `OrderService`가 재료 계산 구조를 직접 알 필요가 줄어들고, 재고 관련 로직도 더 읽기 쉬워진다.

### 4. `OptionGroup`이 옵션 규칙을 직접 판단하게 하면 좋다

`OptionGroup`은 이름, 최소 선택 수, 최대 선택 수, 옵션 목록을 가지고 있다. 그런데 실제 선택 검증의 핵심 로직은 `Menu.validate_selected_options`와 CLI 쪽에 나뉘어 있다.

예를 들어 현재 `Menu`는 모든 그룹을 순회하며 `option in group.options`로 소속 여부와 선택 개수를 계산한다. CLI도 `len(group.options) == 1`인지 여부를 보고 수량 입력인지 선택 입력인지 판단한다. 즉, `OptionGroup`의 규칙이 객체 내부에 캡슐화되기보다 외부 코드에 노출되어 있다.

다음 단계에서는 `OptionGroup`이 다음 질문에 직접 답하도록 만들면 좋다.

- 이 옵션이 이 그룹에 속하는가?
- 이 그룹에서 선택된 옵션 수가 유효한가?
- 이 그룹은 단일 선택 그룹인가, 수량 선택 그룹인가?
- 사용자의 선택 결과를 이 그룹의 규칙에 맞게 검증할 수 있는가?

예를 들어 `contains(option)`, `count_selected(selected_options)`, `validate(selected_options)` 같은 메서드를 둘 수 있다. 그러면 `Menu`는 각 그룹에게 검증을 위임하고, CLI도 그룹 내부 구조를 덜 알게 된다.

### 5. 옵션 수량을 더 명시적으로 표현할 수 있다

현재 샷 추가 2개는 `[shot_option, shot_option]`처럼 같은 `Option` 객체를 두 번 넣어서 표현한다. 이 방식은 간단하고 현재 요구사항에서는 동작한다. 다만 도메인 의미만 놓고 보면 "옵션 하나를 몇 개 선택했는가"라는 개념이 리스트 중복으로 표현되고 있다.

다음 단계에서는 `SelectedOption` 또는 `OptionSelection` 같은 객체를 고려할 수 있다.

```python
@dataclass(frozen=True)
class OptionSelection:
    option: Option
    quantity: Quantity
```

이렇게 하면 "샷추가 2개", "시럽추가 1개"가 코드에서 명확하게 드러난다. 가격 계산과 재고 차감도 리스트에 같은 객체가 몇 번 들어 있는지 세는 방식보다 `quantity`를 기준으로 처리할 수 있다.

단, 이 변경은 `Menu`, `CartItem`, `OrderService`, CLI, 테스트에 영향을 줄 수 있으므로 한 번에 바꾸기보다 별도 리팩터링 단계로 분리하는 편이 좋다.

### 6. 공개 list를 그대로 노출하는 부분은 점진적으로 줄이면 좋다

`Menu.option_groups`, `OptionGroup.options`, `Recipe.items`, `Inventory.items`, `Cart.items`가 모두 공개 list이다. 생성 시점에는 `__post_init__`에서 검증하지만, 생성 후 외부에서 list를 직접 수정하면 검증을 우회할 수 있다.

예를 들어 `Recipe` 생성 후 `items`에 중복 재료를 추가하면 생성자에서 수행한 중복 검증이 무력화된다. 객체지향에서 캡슐화는 생성 시점 검증뿐 아니라, 생성 이후에도 객체가 유효한 상태를 유지하도록 보호하는 것까지 포함한다.

다음 단계에서는 내부 저장은 tuple로 바꾸거나, 외부에는 복사본/읽기 전용 접근자만 제공하는 방향을 고려할 수 있다. 당장 모든 객체를 한 번에 바꿀 필요는 없고, 변경 가능성이 큰 `Recipe.items`, `OptionGroup.options`, `Cart.items`부터 줄이는 것이 현실적이다.

### 7. 타입 검증 방식은 `isinstance` 쪽으로 통일하면 좋다

여러 곳에서 `type(value) is Money`, `type(value) is Menu`처럼 정확히 같은 클래스인지 검사한다. 과제 수준에서는 큰 문제가 아닐 수 있지만, 객체지향 설계 관점에서는 상속이나 대체 구현을 허용하지 않는 방식이다.

이미 일부 파일에서는 `isinstance`를 사용하고 있으므로, 타입 검증 스타일을 `isinstance` 중심으로 통일하면 좋다. 이 변경은 동작 변경이 작고 테스트로 확인하기 쉬워서 초반 리팩터링으로 적합하다.

## 추천 리팩터링 순서

한 번에 구조를 크게 바꾸기보다, 테스트를 유지하면서 작은 단계로 진행하는 것이 좋다.

1. `type(...) is ...` 검증을 `isinstance(...)`로 통일한다.
2. `OptionGroup`에 `contains`, `count_selected`, `validate` 같은 메서드를 추가하고 `Menu.validate_selected_options`의 세부 로직을 위임한다.
3. `Recipe`에 `multiply`, `merge` 같은 계산 메서드를 추가해 재료 계산 책임을 옮긴다.
4. `Cart` 또는 `CartItem`이 선택 옵션 기준 총액과 필요 재료를 더 많이 계산하도록 만든다.
5. `OrderService.checkout`는 계산보다 흐름 조율 중심으로 줄인다.
6. `create_menu`는 동작을 유지한 채 메뉴 정의 데이터와 객체 생성 함수를 분리한다.
7. 필요하다면 마지막에 `OptionSelection`을 도입해 옵션 수량 표현을 명시적으로 바꾼다.

이 순서대로 진행하면 큰 설계 변경을 하면서도 기존 테스트를 계속 안전망으로 사용할 수 있다.

## 종합 평가

현재 코드는 객체지향을 고려하지 않은 코드가 아니다. 값 객체를 만들고, 도메인 계층과 CLI를 분리하고, 테스트로 핵심 흐름을 검증한 점은 분명히 잘했다. 특히 DB가 없는 과제 환경에서 `create_menu`로 기본 메뉴 데이터를 구성한 것도 현실적인 선택이다.

다음 개선의 핵심은 하드코딩 자체를 문제 삼는 것이 아니라, 변경 가능성이 있는 부분을 더 읽기 쉽고 바꾸기 쉬운 형태로 정리하는 것이다. `create_menu`는 현재 역할을 인정하되 데이터 정의와 객체 조립을 분리하는 방향으로, `Recipe`와 `OptionGroup`은 자신이 가진 도메인 규칙을 더 직접 표현하는 방향으로 리팩터링하면 좋다.

결론적으로 지금 구조는 출발점으로 충분히 괜찮다. 이후에는 `OrderService`에 몰린 계산 책임을 `CartItem`, `Order`, `Recipe`, `OptionGroup`, `Inventory`로 조금씩 옮기면 객체들이 단순 데이터 묶음이 아니라 스스로 판단하고 협력하는 구조에 가까워질 것이다.
